Diagnosis: (1) the count of calls grows exponentially, about 1.618 times per extra step (phi^n);
           (2) most of the work is repeated: ways(1) alone is answered 75,025 times for n = 25 while its answer never changes;
           (3) ways(n) depends only on the TWO previous answers, so nothing older than ways(n-2) ever needs to be remembered.

=== PART B: Design objective (measurable) ===
Objective: for n = 30, cut the function calls from 2,692,537 to at most 31 (one step per value) - at least 85,000 times fewer -
           and the time from about 0.1 s to under 0.01 ms; and the same program must work for n = 1,000 and n = 100,000
           with NO RecursionError and constant extra memory (two variables).

=== PART C: Revised design ===
What changed : recursion (top-down, asks the same question again and again) -> bottom-up loop that answers ways(2), ways(3), ... ways(n) once, in order.
Property used: overlapping sub-problems (the same ways(k) is needed many times) and that each answer depends only on the previous two.
Extra memory : none - two variables a and b. A table of all values (O(n)) is only needed when many different n are asked.
New trade-off: no cache is shared between queries, so every query costs O(n) again; many queries -> build the table once (table_up_to).
Pseudocode:
   a <- 1 ; b <- 1                      # ways(0), ways(1)
   repeat for i from 2 to n:
       a, b <- b, a + b                 # slide the window of two values
   return b                             # ways(n)   (n <= 1 returns 1)
Flowchart: q7_flowchart.png (saved in this folder).

=== PART D: Prediction (before implementing) ===
PREDICTED: additions = n - 1 for n >= 2 (n = 10 -> 9, 20 -> 19, 25 -> 24, 30 -> 29); no recursive calls; answers equal the original.
PREDICTED: speed-up of at least 10^4 at n = 30 (2,692,537 calls vs 29 steps); calls go from exponential O(phi^n) to linear O(n).
PREDICTED: for printing ways(1..1000), running the loop separately for every n costs 1+2+...+999 = 499,500 additions; one table pass costs 999.

=== PART F: Defend the final design ===
Objective achieved? Calls for n = 30: 2,692,537 -> 29 additions (about 93,000 times fewer); time at n = 30 reduced by the factor shown in PART E;
   n = 1,000 and n = 100,000 run without any RecursionError. Every answer matched the original for n = 0..30.
New costs: (1) no shared cache between queries - every query is O(n) again (the table pass fixes this for repeated queries at O(n) memory);
   (2) the numbers themselves get large (about 0.69 bits per step), so each addition costs time proportional to the number's size - the
   'O(n) additions' is not O(n) bit operations; the loop for n = 100,000 is still fast but not instant (see times above).
Where the original is still preferable: it is a direct copy of the definition ways(n) = ways(n-1) + ways(n-2), the easiest to read and verify;
   for n up to about 20 (21,891 calls, a few milliseconds) it is perfectly acceptable. I keep it only as the test oracle for the redesign.
